# Харилцан code review хийх чиглэл

Эдгээр нь **шалгах чиглэл, асуултын жишээ** болохоос GitHub дээр нийтэлсэн review биш. Кодыг уншиж, тестийг ажиллуулсны дараа өөрийн ажигласан зүйлд тааруулан бодит comment бичнэ. Нэг reviewer PR бүр дээр дор хаяж 2 утгатай comment нийтэлнэ. `OK`, `Сайн`, `LGTM` гэсэн ганц үгсийг хоёр санал гэж тооцохгүй.

## B → A-ийн seat-validation PR

1. `booking.py`-ийн `return` мөр: «0 суудлыг зөвшөөрөхгүй болгосон нөхцөл харагдаж байна. `seat_count = -1` болон `seat_count = 0` үед хоёул `False` болохыг ямар тестүүд баталж байгааг тайлбарлаж өгнө үү?»
2. `test_seat_validation.py`: «Хязгаарын тохиолдлууд болох сул суудалтай тэнцүү хүсэлт, нэгээр их хүсэлт, сул суудал 0 байх хувилбаруудыг шалгаж байна уу? Эдгээрийн хүлээгдэх үр дүнг захиалгын дүрэмтэй холбон тайлбарлана уу.»

A шаардлагатай бол тест/кодоо засна, эсвэл аль тестээр баталгаажсаныг тодорхой хариулна. Хийгээгүй засварыг хийсэн гэж бичихгүй.

## A → B-ийн trip-status PR (conflict шийдсэний дараа)

1. `booking.py`-ийн нийлсэн `return` мөр: «Conflict шийдэхдээ OPEN нөхцөл болон `0 < seat_count` нөхцөлийг хоёул хадгалсан уу? Нэг талын return-ийг сонгоход ямар бизнес дүрэм алдагдахыг тайлбарлана уу.»
2. `test_combined_policy.py`: «Нийлмэл тестүүд OPEN аялалд 0 суудал хүсэх болон CLOSED аялалд эерэг суудал хүсэх хоёр тусдаа алдааг илрүүлж байна уу? Хоёр feature хамт байгаа эцсийн branch дээр бүх тестийн гаралтыг оруулна уу.»

Нэмэлт ажиглалт: функцээр шалгасан нь суудлыг бодитоор нөөцөлсөн гэсэн үг биш. Энэ lab-ын хүрээнээс гадна зэрэгцээ хүсэлтийг DB transaction дотор шалгаж нөөцлөх шаардлагатай.

## Review нийтлэх

PR → Files changed → мөрийн `+` → comment → Start/Add review → Review changes → Approve эсвэл Request changes → Submit review. Pending review-гээ нийтлээгүй орхивол бусад хүн comment-уудыг харахгүй.

Comment бүрийн permalink-ийг `evidence/report.md`-д тусад нь хадгална. Өөрийн PR-д өөрөө өгсөн санал нь хосын review-г орлохгүй.
